# [[Pre-Engagement]]

Es el estado de preparación para el test de penetración. Durante este apartado se hacen demasiadas preguntas, y algunas son compromisos creados. El cliente nos informará sobre lo que busca y explicaremos en detalle como realizaremos la prueba tan eficiente como sea posible.
![[Pasted image 20260627144842.png]]
El proceso de pro-compromiso consiste de tres componentes escenciales:
* Alcance del cuestionario
* Reunión del compromiso
* Reunión inicial

Antes de que se puedan discutir los detalles anteriores, ambas partes deberán firmar un Acuerdo de Confidencialidad ([[Non-Disclosure Agreement]]). Existen distintos tipos de acuerdos de confidencialidad:
* Unilateral ([[Non-Disclosure Agreement]]): Obliga únicamente a una de las partes a mantener la confidencialidad, mientras que la otra puede compartir la información recibida con terceros.
* Bilateral ([[Non-Disclosure Agreement]]): Obliga a ambas partes a mantener la confidencialidad de la información y de los resultados obtenidos. Es uno de los acuerdos más comunes en el trabajo de un Penetration Tester.
* Multilateral ([[Non-Disclosure Agreement]]): Mantiene la confidencialidad entre más de dos partes. Si se realiza una prueba sobre una red corporativa, todas las partes responsables e involucradas deberán firmar este documento.

Como todo, se pueden realizar ciertas excepciones que normalmente se realizan en casos urgentes, una de las cosas más importantes es conocer quien en la compañia puede contratarnos, más que nada porque esa orden no puede ser aceptada de cualquier empleado, puede ser mentira y nos contratan con la finalidad de hacer daño, por eso mismo, se enlistan los posibles responsables de quien puede contratarnos:

| :--- | :--- |
| Chief Executive Officer | CEO |
| Chief Technical Officer | CTO |
| Chief Information Security Officer | CISO |
| Chief Security Officer | CSO |
| Chief Risk Officer | CRO |
| Chief Information Officer | CIO |

Por eso mismo es importante conocer los puntos de contacto, en esta ocasión al menos 2 para aclarar dudas, situaciones, firmas, permisos, etc. Por otra parte, tambien se deben contemplar que se deben entregar ciertos documentos, para algo profesional se debe documentar al menos 7 etapas en las cuales nos veremos envueltos:

| Document | Timing For Creation |
| :--- | :--- |
| 1. Non-Disclosure Agreement (NDA) | Despues del contacto inicial |
| 2. Scoping Questionnaire | Antes de la cita a pre-reunión |
| 3. Scoping Document | Durante la cita a la pre-reunión |
| 4. Penetration Testing Proposal (Contract/Scope of Work) (SoW) | Durante la cita a la pre-reunión |
| 5. Rules of Engagement (RoE) | Antes del inicio de la reunión |
| 6. Contractors Agreement (Physical Assessments) | Antes del inicio de la reunión |
| 7. Reports | Durante y Despues de la prueba realizada. |

Es altamente recomendable que los documentos sean revisados y adaptados por un abogado antes de que sean preparados.

## [[Scoping Questionnaire]]
Afortunadamente HTB nos brinda una lista de lo que podría ser Scoping Questionnaire, haciendo un poco más sencillo los servicios que podemos ofrecer. Este documento será enviado antes de la reunión para que el encargado sepa y elija algún servicio de los que brindamos.

### Services
* Internal Vulnerability Assessment
* Internal Penetration Test
* Wireless Security Assessment
* Physical Security Assessment
* Red Team Assessment
* External Vulnerability Assessment
* External Penetration Test
* Application Security Assessment
* Social Engineering Assessment
* Web Application Security Assessment

En cada uno de los servicios, se le debería brindar en profundidad nuestros servicios, asegurandonos de que hemos comprendido las necesidades y expectativas del clientes y que hemos comprendido lo de ellos. Además de que nos debería brindar el tipo de evaluación, nombre, dirección, información, entre otras piezas de información crítica, los cuales podrían ser:

### Pieces of Information
* How many expected live hosts?
* How many IPs/CIDR ranges in scope?
* How many Domains/Subdomains are in scope?
* How many wireless SSIDs in scope?
* How many web/mobile applications? If testing is authenticated, how many roles (standard user, admin, etc.)?
* For a phishing assessment, how many users will be targeted? Will the client provide a list, or we will be required to gather this list via OSINT?
* If the client is requesting a Physical Assessment, how many locations? If multiple sites are in-scope, are they geographically dispersed?
* What is the objective of the Red Team Assessment? Are any activities (such as phishing or physical security attacks) out of scope?
* Is a separate Active Directory Security Assessment desired?
* Will network testing be conducted from an anonymous user on the network or a standard domain user?
* Do we need to bypass Network Access Control (NAC)?

Al final, será necesario preguntar sobre el nivel de divulgación de la información y el grado de evasión (Si aplica al tipo de evaluación).

#### Nivel de información que recibe el Pentester
| Tipo | ¿Qué recibe el Pentester? | Simula |
| :--- | :--- | :--- |
| Black Box | Ninguna información. Debe descubrir todo por su cuenta. | Un atacante externo sin conocimiento previo. |
| Grey Box | Información limitada, por ejemplo direcciones IP, rangos CIDR o URL. | Un atacante con cierto conocimiento o un usuario con acceso limitado. |
| White Box | Información completa: diagramas de red, credenciales, código fuente, arquitectura, etc. | Una auditoría profunda donde el objetivo es encontrar la mayor cantidad de vulnerabilidades posibles. |

#### Nivel de evasión
| Tipo | Descripción |
| :--- | :--- |
| No evasivo | No intenta ocultar sus acciones. Utiliza herramientas y técnicas normales, aunque puedan generar muchas alertas. |
| Híbrido-evasivo | Comienza de manera silenciosa y aumenta gradualmente la intensidad de las pruebas para medir en qué momento los sistemas o el personal de seguridad detectan la actividad. |
| Completamente evasivo | Intenta evitar al máximo ser detectado, utilizando técnicas para evadir antivirus, IDS, IPS, EDR y otras herramientas de monitoreo. |

La información otorgada debe brindarnos herramientas y facilitarnos la prueba a realizar, por lo cual es importante estar en contacto con el cliente. Toda esa información debemos reunirla y utilizar lo que más nos convenga.

## [[Pre-Engagement Meeting]]
Una vez que hemos comprendido y recopilado los requerimientos del cliente, podemos pasar al siguiente paso: discutir los componentes iniciales de la prueba y explicárselos al cliente. Toda la información recopilada servirá como base para el Propósito de la Prueba de Penetración, también conocido como Contrato o [[Scope of Work]].

Debemos tener presente que una prueba de penetración sigue un proceso bien definido, por lo que resulta recomendable utilizar un checklist que facilite el desarrollo de cada etapa:
* NDA: Non-Disclosure Agreement (NDA) refers to a secrecy contract.
* Goals: Goals are milestones that must be achieved during the order/project.
* Scope: The individual components to be tested are discussed and defined.
* Penetration Testing Type: When choosing the type of penetration test, we present the individual options.
* Methodologies: Examples: OSSTMM, OWASP, automated and manual unauthenticated analysis.
* Penetration Testing Locations: External: Remote and/or Internal: Internal or Remote.
* Time Estimation: Start and end dates for the penetration test.
* Third Parties: It must be determined via which third-party providers our customer obtains services.
* Evasive Testing: The test of evading and passing security traffic and security systems.
* Risks: Inform our client about the risks involved in the tests and the possible consequences.
* Scope Limitations & Restrictions: Determine which servers, workstations, or other network components are essential for the client's proper functioning.
* Information Handling: HIPAA, PCI, HITRUST, FISMA/NIST, etc.
* Contact Information: Create a list of each person's name, title, job title, e-mail address, phone number, etc.
* Lines of Communication: It should also be documented which communication channels are used.
* Reporting: Any customer-specific requirements the report should contain.
* Payment Terms: Prices and the terms of payment are explained.

Basado en la información del contrato/Scope of Work (SoW), se crea un documento más, llamado [[Rules of Engagement]], por suerte HTB nos brinda un checklist facil de comprender:
* Introduction: Description of this document.
* Contractor: Company name, contractor full name, job title.
* Penetration Testers: Company name, pentesters full name.
* Contact Information: Mailing addresses, e-mail addresses, and phone numbers.
* Purpose: Description of the purpose for the conducted penetration test.
* Goals: Description of the goals that should be achieved with the penetration test.
* Scope: All IPs, domain names, URLs, or CIDR ranges.
* Lines of Communication: Online conferences or phone calls or face-to-face meetings, or via e-mail.
* Time Estimation: Start and end dates.
* Time of the Day to Test: Times of the day to test.
* Penetration Testing Type: External/Internal Penetration Test/Vulnerability Assessments/Social Engineering.
* Penetration Testing Locations: Description of how the connection to the client network is established.
* Methodologies: OSSTMM, PTES, OWASP, and others.
* Objectives / Flags: Users, specific files, specific information, and others.
* Evidence Handling: Encryption, secure protocols.
* System Backups: Configuration files, databases, and others.
* Information Handling: Strong data encryption.
* Incident Handling and Reporting: Cases for contact, pentest interruptions, type of reports.
* Status Meetings: Frequency of meetings, dates, times, included parties.
* Reporting: Type, target readers, focus.
* Retesting: Start and end dates.
* Disclaimers and Limitation of Liability: System damage, data loss.
* Permission to Test: Signed contract, contractors agreement.

## [[Kick-Off Meeting]]
Generalmente se reserva un momento para las partes intereadas, por lo general son varias personas los que participan en la reunión. Usualmente no hay pruebas de Denial of Service (DoS), cuando una vulnerabilidad es encontrada se debe pausar el ataque y notificar para que el equipo evalue si la brecha debe arreglarse inmediatamente, tambien debemos parar si encontramos evidencia de actividad ilegal como compartir archivos u otros casos igual o más criticos. Para esto se deberá contactar con los contactos de emergencia y con la parte legal. Debemos avisar a los clientes que nuestras acciones generarán logs y alarmas en sus aplicaciones de seguridad, de igual forma si se realiza fuerza bruta hay que avisar que algunos usuarios podrían verse afectados por bloqueos. Tambien se debe avisar que se deben conectar con nosotros si una acción generó un efecto negativo en la prueba. Como lo es en todo, es necesario adaptar todas las necesidades a las del cliente, por lo cual es importante que sepan los cambios o las limitaciones.

## [[Contractors Agreement]]
Si la prueba de penetración incluye pruebas fisicas, un contrato de acuerdos es requerida, ya que las leyes aplican de diferente manera por que ya no solo entran cosas virtuales, ahora entra la localización e información aún más personal. Muchas de las veces no se le avisará a los empleados de nuestra presencia, por lo cual el empleado debería reportar y hablar a las autoridades, este acuerdo debería ser nuestro pase de salida de este tipo de casos. Para eso, HTB nos brinda algunas herramientas que nos pueden ayudar a realizar este acuerdo:
* Introduction
* Contractor
* Purpose
* Goal
* Penetration Testers
* Contact Information
* Physical Addresses
* Building Name
* Floors
* Physical Room Identifications
* Physical Components
* Timeline
* Notarization
* Permission to Test
