## Default Configuration
Hay muchos tipos de configuración de DNS, por lo tanto, solo se discutirá unos de los más importantes para mostrar mejor el principio funcional  desde un punto de vista administrativo.  Todos los servidores DNS funcionan con tres diferentes tipos de archivos de configuración:
1. Archivos locales de configuración DNS
2. Archivos de zona
3. Archivos de resolución de nombres inversa
El servidor DNS Bint9 a menudo es muy utilizado en distribuciones Linux. Su archivo de configuración *(named.conf)* se divide aproximadamente en dos secciones: primero, la sección de opciones para la configuración general y segundo, las entradas de zona para los dominios individuales. Los archivos de configuración local suelen ser:
- named.conf.local
- named.conf.options
- named.conf.logs
Contiene el RFC asociado donde podemos personalizar el servidor según nuestras necesidades y nuestra estructura de dominio, con zonas individuales para diferentes dominios. El archivo de configuración *named.conf* está dividido en varias opciones que controlan el comportamiento del servidor de nombres. Se establece una distinción entre opciones globales y opciones por zonas.
Las opciones globales son generales y afectan a todas las zonas. Una opción de zona solo afecta a la zona a la que está asignada. Las opciones que no aparecen en *named.conf* tienen valores predeterminados. Si una opción es global y especifica de una zona, prevalece la opción de zona.

Un archivo de zona es un archivo de texto que describe una zona DNS con el formato de archivo BIND. En otras palabras, es un punto de delegación en el árbol DNS. El formato de archivo BIND es el formato de archivo de zona preferido por la industria y está bien establecido en el software de servidores DNS. Un archio de  zona describe una zona por copmleto, debe contener exactamente un registro SOA y al menos un registro NS. El registro de recursos SOA suele ubicarse al principio de un archivo de zona. El objetivo principal de estas reglas globales es mejorar la legibilidad de los archivos de zona. Un error de sintaxis generalmente provoca que todo el archivo de zona se considere inutilizable. El servidor de nombres se comporta como si esta zona no existiera y responde a las consultas DNS con un mensaje de error SERVFAIL. 
En resumen, aquí todos los registros de reenvio se ingresan según el formato BIND. Esto permite que el servidor DNS identifique a que dominio, nombre de host y función pertenecen las direcciones IP. La zona de transferencia se refiere a transferir zonas a otro servidor DNS, el cual generalmente pasa atraves del protocolo TCP por el puerto 53. A este proceso se le llama *Asynchronous Full Transfer Zone (AXFR)*. Dado que un fallo de DNS suele tener graves consecuencias para una empresa, el archivo de zona se mantiene casi invariablemente idéntico en varios servidores de nombres.
 Cuando los cambios estan hechos, deberia asegurarse que todos los servidores tengan la misma información. La sincronización entre los servidores involucrados se realiza mediante transferencia de zona. Utilizando una clave secreta *rndc-key*, el cual vimos inicialmente en la configuración predeterminada, los servidores se aseguran de comunicarse con su maestro o esclavo. La transferencia de zona implica la simple transferencia de archivos o registros y la detección de discrepancias en los conjuntos de datos de los servidores involucrados.
 Los datos originales de una zona esta ubicado en un servidor DNS, el cual se denomina servidor de nombres principal para esta zona o *primary name server*. Sin embargo, para incrementar la fiabilidad, realizar una simple distribución de carga o proteger el servidor principal de ataques, en la práctica se instalan uno o más servidores adicionales en casi todos los casos, que se denominan servidores de nombres secundarios para esta zona o *secundary name servers*. Para algunos *Top-level domains (TLDs)*, es obligatorio que los archivos de zona de los *second level domains* sean accesibles en al menos dos servidores.
 Las entradas DNS generalmente solo se crean, modifican o eliminan en el servidor primario/principal. Esto se puede hacer editando manualmente el archivo de zona correspondiente o automáticamente mediante una actualización diámica desde una base de datos. Un servidor DNS que actúa como fuente directa para sincronizar un archivo de zona se denomina maestro. Un servidor DNS que obtiene datos de zona de un maestro se demonina esclavo. Un servidor principal siempre es maestro, mientras que un servidor secundario puede ser tanto esclavo, como maestro.
 El servidor esclavo obtiene el registro *SOA* de la zona correspondiente del servidor maestro a intervalos regulares, denominados tiempos de actualización (normalmente de una hora), y compara los números de serie. Si el número de serie del registro SOA del maestro es mayor que el del esclavo, los conjuntos de datos dejan de coincidir.

## Bloque 1: La Mecánica Real (El Modelo Mental)
### 1. La Analogía del Sistema de Archivos Central
Para entender DNS sin abstracciones vacías, imagina que necesitas localizar el expediente físico de una persona en un complejo gubernamental de máxima seguridad con millones de oficinas:
```
[Cliente / Tu Terminal]
       │
       ▼
[Resolver Local / Router / ISP] ──(Asistente de biblioteca con libreta de notas)
       │
       ├─► 1. ¿Quién lleva ".htb"? ──► [Root Server] (".")
       │                                  │
       │   ◄── "Pregunta en la oficina TLD ┘
       │
       ├─► 2. ¿Quién lleva "inlanefreight.htb"? ──► [TLD Server] (".htb")
       │                                              │
       │   ◄── "El servidor de esa empresa es NS1 ────┘
       │
       └─► 3. ¿Cuál es la IP de "app"? ──► [Servidor Autoritativo] (ns1.inlanefreight.htb)
                                              │
           ◄── "La IP exacta es 10.129.20.5" ─┘
```
- **El Resolver Local (Tu Asistente Personal):** Es el servidor DNS de tu router, tu ISP o un resolver público (`8.8.8.8`, `1.1.1.1`). No conoce la respuesta de antemano, pero tiene una libreta donde anota temporalmente lo que descubre (**caché**). Si no lo tiene guardado, él hace el trabajo sucio de consultar a toda la cadena jerárquica por ti.
- **Root Servers (Los Conserjes del Edificio - `.`):** Hay 13 identidades lógicas mundiales (de la `a.root-servers.net` a la `m.root-servers.net`). No saben qué IP tiene una máquina llamada `app`, pero conocen con precisión milimétrica qué servidores gestionan cada terminación de nivel superior (**TLD**). Te dicen: _"Para cualquier cosa que termine en `.htb` o `.com`, ve a la oficina de ese TLD"_.
- **Servidores TLD (Los Archivistas de Sección):** Gestionan dominios de nivel superior (`.com`, `.net`, `.org`, o en laboratorios, `.htb`). Conocen qué servidores de nombres (**Nameservers autoritativos**) fueron delegados para administrar dominios específicos como `inlanefreight.htb`.
- **Servidor Autoritativo (El Dueño Legal del Expediente):** Es el servidor que aloja los archivos maestros de configuración de la zona (`db.inlanefreight.htb`). Tiene la última palabra y la verdad absoluta. Si el autoritativo dice que `app.inlanefreight.htb` apunta a `10.129.20.5`, ningún otro servidor puede contradecirlo.
### 2. Paquete por Paquete: `ping app.inlanefreight.htb`
Cuando ejecutas ese comando en la consola de tu máquina de ataque, el binario `ping` no sabe cómo comunicarse con un nombre; necesita una dirección IP de Capa 3.
```sequenceDiagram
    autonumber
    participant Host as Máquina Local (Attack Host)
    participant OS as OS /etc/hosts & Caché
    participant Resolv as Resolver (/etc/resolv.conf)
    participant Root as Root Server (.)
    participant TLD as TLD Server (.htb)
    participant Auth as Autoritativo (ns1.inlanefreight.htb)
    Host->>OS: ¿Existe resolución para "app.inlanefreight.htb"?
    OS-->>Host: No está en /etc/hosts ni en caché local
    Host->>Resolv: Consulta UDP/53 (Recursiva): "A? app.inlanefreight.htb"
    Resolv->>Root: Consulta UDP/53 (Iterativa): "¿Quién maneja .htb?"
    Root-->>Resolv: Delegación (NS para .htb)
    Resolv->>TLD: Consulta UDP/53 (Iterativa): "¿Quién maneja inlanefreight.htb?"
    TLD-->>Resolv: Delegación (NS: ns1.inlanefreight.htb + Glue Record IP)
    Resolv->>Auth: Consulta UDP/53 (Iterativa): "¿IP (A) de app.inlanefreight.htb?"
    Auth-->>Resolv: Respuesta autoritativa: 10.129.20.5 (TTL: 3600s)
    Resolv-->>Host: Respuesta final: app.inlanefreight.htb = 10.129.20.5
    Host->>Host: Envía ICMP Echo Request a 10.129.20.5
```
1. **Revisión del subsistema local:** El sistema operativo consulta a través de la librería `glibc` (`gethostbyname` o `getaddrinfo`). Lee el orden definido en `/etc/nsswitch.conf` (habitualmente `files dns`). Primero inspecciona `/etc/hosts`. Si no hay coincidencia, recurre a los servidores listados en `/etc/resolv.conf`.
2. **Petición Recursiva del Cliente:** Tu máquina envía un paquete **UDP al puerto 53** del Resolver configurado, activando el flag **RD (Recursion Desired = 1)**: _"Quiero la IP final, resuélvelo por mí"_.
3. **Resolución Iterativa:**
    - El Resolver consulta a un **Root Server**. Este devuelve una referencia (**Referral**) con los registros NS del TLD `.htb`.
    - El Resolver consulta a los servidores del **TLD `.htb`**. Este responde con los registros NS de `inlanefreight.htb` y los **Glue Records** (las IPs de esos servidores NS para evitar un bucle de gallina y huevo).
    - El Resolver consulta al **servidor autoritativo** (`ns1.inlanefreight.htb` en `10.129.20.5`).
4. **Respuesta Autoritativa:** El autoritativo responde con la respuesta final: `app.inlanefreight.htb A 10.129.20.5` con un valor de **TTL (Time to Live)**.
5. **Caché y Entrega:** El resolver almacena la respuesta en su caché local y le entrega la IP a tu máquina. El kernel crea entonces el paquete **ICMP Echo Request** hacia `10.129.20.5`.
### 3. UDP vs TCP en el Puerto 53
DNS opera en ambos protocolos de transporte, pero con propósitos totalmente diferenciados:
- **UDP 53 (Velocidad y baja sobrecarga):**
    - Se utiliza para las **consultas y respuestas ordinarias** del 99% de las aplicaciones.
    - No requiere el triple apretón de manos (_TCP 3-way handshake_ `SYN -> SYN/ACK -> ACK`), lo que reduce drásticamente la latencia y la memoria en servidores que procesan cientos de miles de peticiones por segundo.
    - **El límite histórico:** El RFC 1035 limitaba los mensajes DNS sobre UDP a **512 bytes**. Las extensiones modernas **EDNS0 (RFC 6891)** permiten buffers mayores (ej. 1232 o 4096 bytes), pero si una respuesta supera ese tamaño, el servidor devuelve el paquete con el bit **TC (Truncation) activado**.
- **TCP 53 (Integridad y volumen de datos):**
    - **Fallback por truncado:** Cuando un cliente recibe una respuesta con el flag `TC=1`, descarta el paquete UDP e inmediatamente inicia una conexión **TCP/53** para recibir los datos completos sin pérdida (común en respuestas con firmas DNSSEC o múltiples registros).
    - **Transferencias de Zona (AXFR / IXFR):** Las transferencias de base de datos entre servidores DNS maestro y esclavo manejan miles de líneas. Necesitan control de flujo, confirmación de entrega y segmentación fiable; por tanto, **siempre ocurren sobre TCP 53**.

inlanefreight.htb.    3600    IN    TXT    "atlassian-domain-verification=u98asdf09as8df098a"
```
> [!TIP]
> 
> **Extracción de Inteligencia Ofensiva:**
> - `ip4:10.129.20.0/24`: El administrador acaba de revelar el **rango de red interno** autorizado para enviar correos. Ya tienes un target directo para pivotar o realizar barridos de puertos.
> - `ip4:172.16.5.12`: Indica la existencia de otra subred privada (`172.16.5.0/24`), posiblemente una red de servidores internos o DMZ que no habrías descubierto sin esta consulta.
> - `atlassian-domain-verification`: Confirma que la empresa utiliza productos como Jira o Confluence en la nube o localmente.
## Bloque 3: Anatomía de BIND9 y Configuraciones Vulnerables
### 1. Estructura de Archivos en Linux (`/etc/bind/`)
BIND9 (Berkeley Internet Name Domain) organiza su configuración dividiendo responsabilidades en varios archivos clave:
```
/etc/bind/
├── named.conf           <- Archivo raíz; solo incluye los demás archivos
├── named.conf.options   <- Directivas de seguridad globales, recursión y reenvíos
├── named.conf.local     <- Declaración de zonas locales (forward y reverse)
└── zones/
    ├── db.inlanefreight.htb   <- Archivo de zona directa (Registros A, MX, etc.)
    └── db.10.129.20           <- Archivo de zona inversa (Registros PTR)
```
- **`named.conf`:** Archivo base que lee el servicio `named`. Normalmente contiene sentencias `include` que apuntan a `named.conf.options`, `named.conf.local` y `named.conf.default-zones`.
- **`named.conf.options`:** Controla el comportamiento del motor DNS a nivel de red: qué interfaces escuchan peticiones, qué servidores reciben reenvíos (**forwarders**) y las políticas de acceso (ACLs, DNSSEC, recursión).
- **`named.conf.local`:** Aquí se define qué dominios es capaz de responder este servidor:
```zone "inlanefreight.htb" {
        type master;
        file "/etc/bind/zones/db.inlanefreight.htb";
    };
```
- **Archivos de zona (`db.dominio`):** Contienen los registros reales. Comienzan con la directiva `$TTL` y el bloque `SOA`, seguido de los registros de recursos (NS, A, CNAME, etc.).
### 2. Configuración Vulnerable Explicada
Un error clásico ocurre en `/etc/bind/named.conf.options` o dentro de la definición de zona en `named.conf.local`:
```
// Archivo: /etc/bind/named.conf.options
options {
    directory "/var/cache/bind";

    // VULNERABILIDAD 1: Recursión abierta a cualquier cliente
    recursion yes;
    allow-recursion { any; };
    allow-query-cache { any; };

    // VULNERABILIDAD 2: Transferencia de zona sin restricción de IP
    allow-transfer { any; };

    listen-on port 53 { any; };
    listen-on-v6 { any; };
    dnssec-validation auto;
};
```
#### ¿Por qué comete este error el administrador?
1. **Resolución de problemas apresurada ("Troubleshooting Mode"):** Al configurar un servidor secundario (slave) para alta disponibilidad, la replicación falla por problemas de permisos o firewalls. El administrador prueba con `allow-transfer { any; };` para descartar errores de BIND, la sincronización funciona, y la directiva **queda olvidada en producción**.
2. **Confusión entre Servidor Autoritativo y Servidor Caché:** Piensan que para que los clientes de la empresa puedan navegar a Internet, el servidor debe tener `recursion yes;` abierto para todo el mundo, en lugar de restringir la recursión exclusivamente a la subred interna mediante una ACL (`allow-recursion { 10.129.20.0/24; };`).
#### Consecuencias Ofensivas:
- **`allow-transfer { any; };`**: Cualquier atacante puede descargar toda la topología de la red mediante una única consulta `AXFR`.
- **`recursion yes;` (Open Resolver):** Permite que atacantes usen el servidor para ataques de denegación de servicio por **amplificación DNS** (enviar consultas de registros TXT grandes con IP de origen falseada hacia la víctima) o realizar **DNS Cache Poisoning** / envenenamiento de caché si la validación DNSSEC no está configurada de forma estricta.
## Bloque 4: Técnicas de Ataque y Enumeración (Paso a Paso)
### 1. Transferencia de Zona (AXFR)
#### Mecánica a Bajo Nivel
La transferencia de zona es el mecanismo de replicación oficial definido en el RFC 5936. Cuando un servidor DNS secundario arranca, le solicita al primario una copia íntegra de la zona para mantener la redundancia.
Dado que la respuesta puede contener decenas de miles de registros, **AXFR se ejecuta obligatoriamente sobre una sesión TCP/53**. El cliente envía una consulta de tipo `AXFR`, y el servidor devuelve todos los registros contenidos entre dos registros `SOA` idénticos (uno al inicio y otro al final de la transmisión).
#### Ejecución con `dig`
Para solicitar una transferencia de zona contra el servidor objetivo:
```
dig axfr @10.129.20.5 inlanefreight.htb
```
Si el servidor es vulnerable, obtendrás una extracción masiva de datos:

DNS Zone file
```
; <<>> DiG 9.18.24 <<>> axfr @10.129.20.5 inlanefreight.htb
;; global options: +cmd
inlanefreight.htb.      3600    IN    SOA    ns1.inlanefreight.htb. admin.inlanefreight.htb. 2024041501 3600 1800 604800 86400
inlanefreight.htb.      3600    IN    NS     ns1.inlanefreight.htb.
inlanefreight.htb.      3600    IN    A      10.129.20.5
dc01.inlanefreight.htb. 3600    IN    A      10.129.20.2
dev.inlanefreight.htb.  3600    IN    A      10.129.20.100
gitlab.inlanefreight.htb. 3600  IN    A      10.129.20.105
vpn.inlanefreight.htb.  3600    IN    A      10.129.20.254
inlanefreight.htb.      3600    IN    SOA    ns1.inlanefreight.htb. admin.inlanefreight.htb. 2024041501 3600 1800 604800 86400
;; Query time: 4 msec
;; SERVER: 10.129.20.5#53(10.129.20.5) (TCP)
;; MSG SIZE  rcvd: 287
```
#### ¿Qué hacer si la zona principal falla (`Transfer failed`)?
En entornos empresariales o máquinas de HTB (como _Resolute_ o _Cascade_), los administradores bloquean AXFR en el dominio principal (`inlanefreight.htb`), pero dejan configuradas subzonas de desarrollo o internas en archivos separados sin la restricción.
1. Identifica posibles subdominios mediante fuerza bruta o registros NS.
2. Si descubres que existe un subdominio como `internal.inlanefreight.htb` o `dev.inlanefreight.htb`, **lanza el AXFR directamente contra esa subzona específica**:
```
# La zona raíz falla:
dig axfr @10.129.20.5 inlanefreight.htb
; Transfer failed.

# Pero la subzona interna está mal configurada:
dig axfr @10.129.20.5 internal.inlanefreight.htb
```
### 2. Consultas CHAOS: Identificación de la Versión de BIND
BIND implementa una clase especial de red llamada **CHAOS (CH)**, diseñada originalmente para redes Chaosnet en el MIT. Si no ha sido deshabilitada en la configuración (`version none;`), expone la versión del software compilado mediante la consulta del registro `version.bind`.
Comando de explotación:
```
dig @10.129.20.5 version.bind txt chaos +short
```
Salida típica:
```
"9.16.1-Ubuntu"
```
Otras consultas útiles en la clase CHAOS:
```
# Nombre del host interno del servidor
dig @10.129.20.5 hostname.bind txt chaos +short

# Identificador de autor del binario
dig @10.129.20.5 authors.bind txt chaos +short
```
> [!TIP] **Impacto en Pentesting:**
> Conocer la versión exacta (`9.16.1-Ubuntu`) te permite saltar a bases de datos de vulnerabilidades (NVD / Exploit-DB) y buscar CVEs concretos que afecten a esa compilación específica (como denegaciones de servicio por paquetes maliciosos o escapes de memoria).
### 3. Resolución Inversa (PTR Sweeps)
Cuando AXFR está bloqueado y no tienes una lista de subdominios, la resolución inversa explota el espacio de nombres especial **`in-addr.arpa`** para convertir direcciones IP en nombres FQDN.
#### Consulta Individual
```
dig @10.129.20.5 -x 10.129.20.2 +short
```
Respuesta:
```
dc01.inlanefreight.htb.
```
#### Scripting en Bash para Barrido Rápido de Subred (Class C Sweep)
Puedes barrer un segmento `/24` completo en segundos sin instalar herramientas adicionales:
```
for ip in $(seq 1 254); do
    result=$(dig @10.129.20.5 -x 10.129.20.$ip +short)
    if [ -n "$result" ]; then
        echo -e "[+] 10.129.20.$ip \t-> $result"
    fi
done
```
Salida del ataque en consola:
```
[+] 10.129.20.2   -> dc01.inlanefreight.htb.
[+] 10.129.20.5   -> ns1.inlanefreight.htb.
[+] 10.129.20.100 -> dev-portal.inlanefreight.htb.
[+] 10.129.20.105 -> gitlab-internal.inlanefreight.htb.
[+] 10.129.20.254 -> fw-edge.inlanefreight.htb.
```
Este método descubre hosts críticos de infraestructura que los administradores no asocian a registros web públicos.
### 4. Fuerza Bruta: Subdominio DNS vs Virtual Host (vHost)
Esta es una de las mayores fuentes de confusión en evaluaciones de pentesting. Operan en capas totalmente distintas:
```mermaid
[Cliente] ──(Capa 3/4: UDP/53)──► Servidor DNS ──► ¿Existe "dev.inlanefreight.htb"? 
                                                    ├── SI: Devuelve IP (10.129.20.5)
                                                    └── NO: NXDOMAIN (Falla la conexión)

Si el DNS resuelve la IP:
[Cliente] ──(Capa 7: HTTP TCP/80)──► Servidor Web (Nginx/Apache en 10.129.20.5)
                                     Envía cabecera: "Host: dev.inlanefreight.htb"
                                     El servidor web enruta al directorio /var/www/dev
```
- **Subdominio DNS Real (Capa 3/4 - Infraestructura de Red):**      
    - Se consulta al servidor DNS.
    - Si el subdominio no existe en la base de datos DNS, el servidor responde con el código de estado **`NXDOMAIN` (Non-Existent Domain)**.
    - El sistema operativo ni siquiera intenta iniciar una conexión TCP contra ninguna IP porque no sabe a dónde enviarla.
- **Virtual Host / vHost (Capa 7 - Aplicación Web):**
    - Ocurre cuando un servidor web (Nginx, Apache, IIS) aloja **múltiples sitios web bajo una sola dirección IP**.
    - El servidor web decide qué sitio mostrar inspeccionando la cabecera HTTP:
     HTTP
        ```
        GET / HTTP/1.1
        Host: admin.inlanefreight.htb
        ```
    - **El dilema ofensivo:** Si un administrador crea un vHost en Apache (`admin.inlanefreight.htb`), pero **olvida registrarlo en el servidor DNS**, la enumeración por `dnsenum` o `dig` jamás lo encontrará. Para encontrarlo, debes enviar peticiones HTTP forzando la cabecera `Host` mediante herramientas como `ffuf` o `gobuster` contra la IP del servidor web.
#### Automatización 1: `dnsenum` (Fuerza Bruta de Subdominios DNS)
`dnsenum` automatiza la recolección de registros, la prueba de AXFR y el ataque de diccionario:
```
dnsenum --dnsserver 10.129.20.5 \
        --enum inlanefreight.htb \
        -f /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
        -r
```
- `--dnsserver`: Fuerza la consulta al servidor objetivo bajo prueba.
- `-f`: Especifica el diccionario de subdominios.
- `-r`: Realiza recursión sobre los subdominios encontrados.
#### Automatización 2: Script Bash Rápido con `dig`
Si estás en un entorno restringido o en una máquina comprometida donde solo dispones del binario `dig`:
```
#!/bin/bash
TARGET_DNS="10.129.20.5"
DOMAIN="inlanefreight.htb"
WORDLIST="/usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt"

echo "[*] Iniciando fuerza bruta DNS contra $DOMAIN en $TARGET_DNS..."

while read -r sub; do
    fqdn="${sub}.${DOMAIN}"
    ip=$(dig @${TARGET_DNS} ${fqdn} +short A)
    if [ -n "$ip" ]; then
        echo -e "[HIT] ${fqdn} \t-> ${ip}"
    fi
done < "$WORDLIST"
```
