# [[Structured Troubleshooting Methods|Métodos de Resolución de Problemas Estructurados]]
Basándonos en el [[Modelo OSI]] como una guía sistemática para rastrear y encontrar fallas en la infraestructura, existen distintas metodologías estructuradas que podemos seguir para solucionar un problema de manera eficiente:

 
| Método de Diagnóstico | Punto de Partida (Modelo OSI) | ¿Cuándo es ideal utilizarlo? |
| :--- | :--- | :--- |
| **[[Bottom-Up]]** | Capa 1 (Física) hacia arriba. | Cuando se sospecha de problemas de hardware, cables o conectividad física inicial. |
| **[[Top-Down]]** | Capa 7 (Aplicación) hacia abajo. | Cuando el problema está plenamente identificado en el software o aplicaciones. |
| **[[Divide and Conquer]]** | Capas centrales (Capa 3 o 4). | Cuando se desconoce por completo la causa raíz y se quiere ahorrar tiempo. |
| **[[Follow the Path]]** | Ruta de extremo a extremo (Flujo). | Para reducir el alcance eliminando dispositivos que no están en el camino de los datos. |
| **[[Substitution]]** | Reemplazo físico o lógico de piezas. | Casos específicos donde se cuenta con refacciones o componentes de respaldo idénticos. |
| **[[Comparison]]** | Contraste con un perfil funcional. | Útil cuando no se encuentra la causa raíz pero se tiene un equipo idéntico operando bien. |
| **[[Educated Guess]]** | Hipótesis basada en experiencia. | Exclusivo para ingenieros experimentados ante fallas conocidas o patrones repetitivos. |
 

---

### 1. Bottom-Up (De abajo hacia arriba)
Podemos iniciar la revisión de abajo hacia arriba basándonos estrictamente en el orden del modelo OSI. Este enfoque consiste en verificar primero los componentes físicos (cables, conectores, tarjetas NIC), continuar con los switches (Capa 2), seguir con los routers (Capa 3) y de ahí ascender sucesivamente hasta llegar a las aplicaciones.

### 2. Top-Down (De arriba hacia abajo)
Se utiliza este método principalmente cuando el problema ya ha sido acotado o preidentificado en los niveles superiores. Generalmente, ocurre cuando existe algún inconveniente dentro del software o la configuración de una aplicación específica. Se recomienda aplicar este método para analizar la causa desde la capa de aplicación, documentar el comportamiento del sistema y registrar la solución implementada sin interactuar con el cableado o la red física.

![[Pasted image 20260616221754.png]]

### 3. Divide and Conquer (Divide y vencerás)
Se suele utilizar este método cuando se desconoce por completo la causa del problema. Consiste en analizar una capa intermedia del modelo OSI para identificar rápidamente en qué nivel se encuentra la falla. Dependiendo de los resultados obtenidos, se puede mutar a otro método de solución de problemas o enfocarse directamente en la dirección donde se detectó el inconveniente. 

*   *Ejemplo práctico:* Si los usuarios no pueden acceder a una página web, pero sí pueden realizar un `ping` exitoso al servidor, el problema probablemente se encuentra en una capa superior a la Capa 3 (como la capa de transporte o aplicación). En cambio, si los usuarios ni siquiera pueden realizar un `ping` al servidor, la falla podría encontrarse en las capas inferiores del modelo OSI (capa física, enlace de datos o red).

### 4. Follow the Path (Seguir la ruta)
Es uno de los métodos más sencillos y lógicos, ya que consiste en seguir detalladamente la ruta física y lógica donde se presenta el problema desde su origen. Si el inconveniente comienza desde el usuario, se realiza un seguimiento del proceso paso a paso (salto por salto) hasta lograr recrear la falla y encontrar el punto exacto donde se interrumpen los datos. El objetivo principal de este método es reducir drásticamente la cantidad de enlaces y dispositivos involucrados en el diagnóstico, dejando únicamente aquellos elementos sospechosos y descartando los componentes que no tienen relación con el flujo afectado.

### 5. Substitution (Sustitución)
Este método consiste en intercambiar un servicio, cable, módulo o dispositivo entero por otro que se encuentre en perfecto estado de funcionamiento. Si después del cambio el problema se soluciona, se determina inmediatamente que la causa raíz estaba relacionada con el componente reemplazado; en caso contrario, se debe regresar la pieza original y continuar investigando otras posibles variables. Este método funciona muy bien en casos específicos, como la sustitución de un router de borde o algún componente crítico de la infraestructura. Permite comprobar de manera rápida si el problema continúa o desaparece, aunque su aplicación puede ser limitada dependiendo de la disponibilidad de equipos o refacciones de reemplazo en el inventario.

### 6. Comparison (Comparación)
Consiste en comparar un dispositivo o componente que presenta fallas con otro que se encuentre configurado y funcionando correctamente dentro del mismo entorno para identificar posibles diferencias en sus variables. Es una herramienta sumamente útil cuando no se logra encontrar la causa raíz mediante otros métodos, ya que permite detectar de forma visual o textual discrepancias en las líneas de comando, versiones de firmware, configuraciones de puertos o elementos de hardware que puedan estar generando el inconveniente.

### 7. Educated Guess (Conjetura informada)
Este método es el menos estructurado de todos, ya que depende principalmente de la experiencia previa y el conocimiento acumulado de la persona encargada de realizar el diagnóstico. Se basa en la identificación instantánea de patrones, problemas conocidos en ciertas marcas de hardware y soluciones rápidas a partir de situaciones similares que hayan ocurrido anteriormente (lecciones aprendidas). Es una metodología ágil y útil principalmente cuando el encargado cuenta con amplia experiencia en la infraestructura actual, permitiendo encontrar soluciones en cuestión de minutos; sin embargo, puede ser muy poco efectiva o inducir a errores si no se tiene el suficiente conocimiento del entorno o de la falla en cuestión.
